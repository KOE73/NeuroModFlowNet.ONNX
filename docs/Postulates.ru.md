# Постулаты NeuroModFlowNet.ONNX / Pipeline: постулат, причина, пример

Последняя сверка с кодом: **2026-09-22**.

> **Примечание о поддержке документа.** Постулаты описывают, как проект *задуман*, а код показывает, как он *есть*.
> Эти две картины расходятся незаметно: старый fallback остаётся в catch-блоке, параметр забывают добавить в ключ кэша,
> новая стадия кладёт config в поля op-а. Поэтому документ нужно **периодически сверять с реальностью**: при возвращении
> к проекту после паузы, перед крупным рефакторингом и после добавления новой VM-стадии или сервиса. Каждая сверка
> обновляет дату вверху. Постулат, который код нарушает и это нарушение осознанно принято, надо либо переписать, либо
> удалить, но не оставлять как «красивую неправду».

Аксиомы (заложены с самого начала) и постулаты, выросшие из практики, формально не разделяются, но у каждого есть
пример: если пример начинается с «так было / так стало», значит постулат появился по ходу дела.

Источники: `AGENTS.md`, `src/NeuroModFlowNet.Pipeline/docs/Architecture.ru.md`,
`src/NeuroModFlowNet.Pipeline/docs/InstructionNaming.ru.md`, `docs/architecture/tracker_and_source_config.ru.md`.

## 1. Философия: VM как ассемблер

### 1.1. Пайплайн это линейная программа инструкций над именованными регистрами

**Постулат.** Обработка кадра описывается как timeline инструкций (`VmProgram`), которые читают и пишут именованные
регистры `VmRunContext`. Не граф объектов, не DI-дерево, не цепочка делегатов.

**Почему.** Ассемблерная модель делает hot path прозрачным: каждая инструкция измеряется отдельно, после неё виден снимок
регистров с типом, формой и местом памяти. Главная цель проекта, GPU-resident обработка, проверяется не по словам, а по trace.

**Пример.** Trace одного запуска показывает строку `Op_Onnx_PadResize_FP16_NCHW` и после неё регистр `image.model`
c `VarMemoryLocation.Gpu` и формой `1x3x640x640`. Если следующая строка это `Model_Yolo` со входом на CPU, проблема видна
сразу, без профилировщика.

### 1.2. Fallback запрещён везде

**Постулат.** Если явно выбранный backend, opset, оператор, layout, тип данных или provider path недоступен, код падает.
Никаких скрытых переходов на CPU, другой Execution Provider, другую реализацию или приближённую семантику.

**Почему.** Скрытый fallback молча превращает GPU-пайплайн в CPU-пайплайн и маскирует ошибку конфигурации. Либо команда
работает быстро и точно в заявленном режиме, либо не работает вообще.

**Пример (так было / так стало).** В `Op_Onnx_TensorTransformBase.EnsureContext()` стоял `catch`, который на любую
ошибку, включая OOM и битую модель, тихо создавал CPU-контекст. Убрано. На уровне сессии `OnnxModel` теперь выставляет
`session.disable_cpu_ep_fallback = 1`. Второй пример: для `rec.onnx` PaddleOCR strict CUDA не работает, потому что
ONNX Runtime назначает часть узлов на CPU EP. Решение не «разрешить CPU EP», а явно выбрать TensorRT для Rec-сервиса
на init.

### 1.3. Frontend один, kernel выбирается строго на init

**Постулат.** У операции может быть несколько реализаций под opset/backend/provider, но выбор делается при создании и
фиксируется. Во время `ExecuteAsync` нельзя пробовать другие реализации.

**Почему.** Runtime-переключение это тот же fallback, только внутри одной операции. Плюс оно ломает измеримость: benchmark
одной команды перестаёт быть benchmark-ом одного алгоритма.

**Пример.** `PaddleRecRoiPrepareAlgorithm` имеет три варианта: `PerRegionGridSampleConcat`, `BatchedGridSample`,
`BatchedGridSampleFromMatrices`. Вариант передаётся параметром `Op_Onnx_ExtractObbToPaddleRec_FP32_NCHW`, каждый
измеряется отдельно. Если backend не поддерживает выбранный, операция падает на init.

## 2. Память и размещение данных

### 2.1. Нет ручного управления CPU/GPU памятью

**Постулат.** Все переносы между CPU и GPU идут через ONNX-графы или механизмы ONNX Runtime. Никаких прямых CUDA-копирований.

**Почему.** Пайплайн должен переноситься между CUDA, TensorRT, DirectML и CPU без переписывания. Прямые CUDA-вызовы
привязывают код к одному вендору.

**Пример.** `Copy_OrtTensor_To_ModelDevice` переносит тензор динамическим графом `Identity`, собранным `IdentityBuilder`
и запущенным на нужном Execution Provider. Тест `Copy_OrtTensor_To_ModelDeviceTests` проверяет через
`OrtValueMemoryAssert`, что результат действительно лежит в provider memory.

### 2.2. Неявные копирования контролируются и запрещаются

**Постулат.** Данные для GPU-операции явно готовятся шагом переноса. Валидатор размещения проверяет входы и выходы каждой
инструкции и запрещает скрытый перенос.

**Почему.** Когда ONNX Runtime сам копирует CPU-тензор на GPU при несоответствии провайдеров, это самая дорогая и самая
незаметная потеря на hot path.

**Пример.** `DeviceCompatibilityValidator` в warmup-проходе падает с сообщением
`[COMPATIBILITY ERROR] Инструкция ... выполняется на GPU, но входящая переменная ... расположена на CPU. Добавьте явный
шаг переноса`. Warmup специально гоняет программу целиком, чтобы поймать это до production-кадров.

### 2.3. Внутренний целевой формат изображения это NCHW FP16/FP32

**Постулат.** OpenCV `BGR U8 HWC/NHWC` считается bridge-форматом на границе с `Mat`. Для model pipeline в первую очередь
развиваются `NCHW` варианты `FP16`/`FP32`, остальные layout только по реальной необходимости.

**Почему.** Модели ждут NCHW. Каждая лишняя конверсия layout на GPU это отдельный ORT call и промежуточный тензор.

**Пример.** Набор операторов: `Op_Onnx_Resize_FP16_NCHW`, `_FP32_NCHW` и один `_U8_NHWC` для входа от `Mat`. Первая
операция после загрузки это fused `Op_Onnx_BgrU8Hwc_To_RgbFP16Nchw_Div255`, после неё всё живёт в NCHW.

### 2.4. Lifetime GPU intermediates: контекст умирает раньше инструкции

**Постулат.** Если инструкция выделяет промежуточный `OrtValue` через provider allocator или session, `VmRunContext`
с этими значениями освобождается раньше долгоживущей инструкции и её allocator/session. Тесты повторяют этот порядок.

**Почему.** `OrtValue`, выделенный allocator-ом сессии, нельзя освобождать после сессии: это падение в native-коде, которое
не ловится и воспроизводится нестабильно.

**Пример.** В тестах операторов контекст создаётся через `VmRunContextFactory`, диспозится в конце теста, а инструкция
диспозится после него. Порядок в тесте это не «стилистика», а воспроизведение production-контракта владения.

## 3. Структура программы и данных

### 3.1. Три категории данных: структура, per-source config, per-source state

**Постулат.** Структура программы одна на все источники. Per-source config (перспектива, дисторсия, зоны, пороги) это
данные в `VmGlobalMemory`, стабильные годами. Per-source state (трекер) это объект в `VmGlobalMemory`, меняется каждый
кадр. Op держит только строковые ключи.

**Почему.** Если config лежит в полях op-а, экземпляр программы намертво привязан к камере: «рецепт» перестаёт быть
рецептом. Если config и state в памяти контроллера, один builder собирает программу для любой камеры.

**Пример (так было / так стало).** Первая версия трекера положила `StartZone`/`EndZone` в поля `Op_Track`. Это вернуло
связку «экземпляр программы = камера». Переделано: `Op_Track` читает `TrackerFrameOptions` из `GlobalMemory` по ключам
на каждом кадре, сам трекер создаётся через `GlobalMemory.GetOrAdd("tracker.<name>", factory)`. Бонус, который получили
бесплатно: hot-reload зон атомарной подменой значения.

### 3.2. Контроллер = источник

**Постулат.** `VmController` создаётся на `SourceId`, владеет своей `VmGlobalMemory`, своим `MaxInFlight` и своим плотным
`RunId`. Общее между контроллерами это ресурсы (`IVmResource`) и кэш kernels, а не программа и не память.

**Почему.** Изоляция по источнику получается автоматически: не нужно ключевать state по `SourceId`, не нужно упорядочивать
кадры разных камер в один поток, `MaxInFlight` одной камеры не отбирает слоты у другой.

**Пример (так было / так стало).** Сценарий «10 камер, у каждой своя предобработка, дальше общий путь». Рассматривались
варианты «пред-VM на камеру + основная VM» и «одна VM со switch по камере». Оба ломают изоляцию: общая память, общий
порядок `RunId`, трекер одной камеры ждёт кадр другой. Решение (ADR-001): десять контроллеров, каждый исполняет цепочку
`[prepare_i, common]` одним `VmRunContext`; общее исполнение достигается батчинг-ресурсом модели и глобальным кэшем
операторов. Важно: делить надо код (builder), а не экземпляр `VmProgram`, потому что у `Op_Onnx_TensorTransformBase`
есть `IoBinding` и `executionLock` на экземпляр.

### 3.2a. Цепочка программ исполняется одним контекстом и не пересекает контроллеры

**Постулат.** `VmController` исполняет список программ по порядку одним `VmRunContext`. Цепочка семантически равна
одной склеенной программе: `Stop` завершает весь запуск, `Fail` проваливает его, метки локальны для программы, trace
помечает программу. Композиция делается при сборке контроллера, не в runtime (`call`/`switch` не вводятся).

**Почему.** Регистровый файл принадлежит запуску одного контроллера. Пока цепочка внутри контроллера, все гарантии VM
(`RunId`, `GlobalMemory`, sync gates, владение `OrtValue`) сохраняются бесплатно. Любой перенос контекста между
контроллерами требует отдельного протокола владения и ломает изоляцию источника.

**Пример.** `new VmController(options, [prepareForCamera(cfg), BuildCommon()])`. Контракт между программами это имена
регистров (`image.model`, `transform.model`), проверяется `VarRequirement.Reads` и `DeviceCompatibilityValidator` в
warmup. Детали и отвергнутые варианты: `docs/architecture/ADR-001_program_chain_per_controller.ru.md`.

### 3.3. Синхронизация по RunId, а не по номеру кадра

**Постулат.** Ordered-точки ждут `RunId`, который выдаётся каждому *принятому* запуску, а не номер кадра источника.

**Почему.** Кадры пропускаются до VM (host решает, принимать ли работу). Ожидание номера кадра, которого VM никогда не
запускала, вешает ordered-точку навсегда.

**Пример.** `VmSyncGateRegistry` хранит закрытые `RunId` и replay-ит их в gates, созданные позже: если run упал до того,
как дошёл до критической секции, поздно созданная секция не ждёт его вечно. Сюда же drop-tolerance: run, отменённый
внутри секции, отпускает следующий через `NotifyRunClosed`.

### 3.4. Ordered critical section вместо barrier для stateful стадий

**Постулат.** Инструкции можно назначить `SyncGate`; VM оборачивает её тело в «дождаться очереди по `RunId`, выполнить
эксклюзивно, отпустить следующий». Barrier (`OrderedSyncInstruction`) остаётся для случаев «только порядок».

**Почему.** Stateful стадия (трекер) требует и порядок, и взаимоисключение, покрывающее тело op-а, иначе age и missed
frames считаются на перемешанных кадрах.

**Пример (так было / так стало).** Разбор `VmSyncGate.ArriveAndWaitAsync` показал, что `OrderedSyncInstruction` это
barrier, а не mutex: run N отпускался сразу, `nextRunIdToRelease` становился N+1, и N+1 тоже отпускался сразу. Два кадра
одновременно в трекере. Введён `OpDescriptor.SyncGate` с `AcquireInOrderAsync`/`Release`; `Op_Track` сам lock не берёт.

### 3.5. Регистры именуются строками

**Постулат.** Внешний контракт регистров строковый. Компиляция имён в быстрые слоты возможна позже, публичная модель от
этого не меняется.

**Почему.** JSON-конфигурация, скрипты, trace и debug-инструменты работают по именам. Строка это единственный формат,
который читают и человек, и конфиг, и VM-отладчик.

**Пример.** Avalonia-demo получила JSON-driven конфигурацию inference и OCR postprocessing (коммит 11aeda4). Labs
`NeuroModFlowNet.Pipeline.VMDebug` показывают регистры по именам. Смена на числовые слоты сломала бы оба потребителя.

### 3.6. Обратные координаты это именованные регистры с данными transform

**Постулат.** Графическая операция пишет `OrtValue` и, если запрошено, отдельный регистр с `ICoordinateBackTransform`
(данные и тип, не delegate). `Op_Map_Coordinates` применяет один named transform к одному payload-регистру и пишет новый.

**Почему.** Жёсткая структура `scale/pad` описывает только letterbox. Реальная цепочка это crop, resize, rotate,
perspective, undistort в произвольном порядке, и промежуточные координатные регистры должны оставаться видимыми для
следующих инструкций.

**Пример (так было / так стало).** В старом слое `LetterboxCoordinateMapper` хранил `scale`, `padX`, `padY`. Когда для
OCR появилась цепочка «source → perspective → PadResize → OBB-детекция → remap → crop ROI»
(`ImgTextToObbOrtValueIntegrationTests`), scale/pad не могли выразить перспективу. Появились
`PerspectiveCoordinateBackTransform`, `PadResizeCoordinateBackTransform`, `CropCoordinateBackTransform` и одна команда
применения.

### 3.7. Политика формы явная

**Постулат.** Если transform может изменить геометрический класс фигуры, нельзя молча врать исходным типом. Режимы:
`PreserveShape`, `BoundingBox`, `BoundingOBB`, `Quad`, `RejectIfShapeChanges`.

**Почему.** Осевой `YoloBox` после perspective перестаёт быть осевым прямоугольником. Вернуть его как `YoloBox` значит
подсунуть downstream неверную геометрию без предупреждения.

**Пример.** `CoordinateMappingShapePolicy` в `NeuroModFlowNet.Pipeline/Coordinates`. Обратный маппинг OBB через
перспективу отдаёт quad, а не «примерно такой же OBB».

## 4. Инструкции и сервисы

### 4.1. Ops работают с готовыми typed значениями

**Постулат.** `Op_*` не знает внутренности сети, batching, output names, decode layout. Читает регистры, преобразует
готовые типизированные значения, пишет регистры.

**Почему.** Иначе каждая инструкция становится доменной и непереносимой, а смена модели требует переписывания VM-команд.

**Пример.** `Op_DetectionsFromYoloObb` превращает `YoloObb[]` в нейтральный `TrackDetection[]`. `Op_Track` вообще не
знает про YOLO и ONNX: он лежит рядом с ONNX-слоем только потому, что там его единственные потребители.

### 4.2. Вызов сервиса отделён от op-а, результат сервиса всегда массив

**Постулат.** Inference, OCR recognition, batching, native output access и decode живут в service/endpoint слое.
VM-инструкция тонкая: регистры → сервис → `T[]` в регистр.

**Почему.** Сервис делят все контроллеры, поэтому именно он собирает batch из заявок разных VM. Массив как результат
убирает частные случаи для детекторов, OCR, top-k и будущих моделей.

**Пример.** PaddleOCR Rec OrtValue service (коммит 94c7ebc) принимает `[N, 3, 48, W]` от каждой VM-заявки, объединяет через
ONNX concat, запускает `rec.onnx`, декодирует в `OcrResult[]` и режет результат обратно по фактическому числу ROI каждой
заявки. Старый `RunnerResource<List<Mat>, ...>` для этого пути не используется.

### 4.3. Batch assembly без CPU round-trip, padding невидим для VM

**Постулат.** Если входные `OrtValue` на GPU, объединение в batch делается ONNX-графом на выбранном provider. При
фиксированном batch модели padding-слоты не видны VM; decoder возвращает результаты только реальных заявок.

**Почему.** Спуск на CPU ради concat уничтожает смысл GPU-resident пайплайна. Отдельный zero-tensor для padding это ещё
одна подготовительная операция на hot path.

**Пример.** `ConcatOrtValueBatchInputAssembler` собирает batch графом concat. Padding-слот привязывается к уже
существующему реальному input `OrtValue`, а не к отдельному чёрному тензору.

### 4.4. Fixed capacity как явный параметр, а не скрытое поведение

**Постулат.** `maxRoiCount` это параметр команды. Фактическое число пишется отдельным регистром, переполнение обрабатывается
только по явной политике `Fail` или `Truncate`.

**Почему.** TensorRT надёжнее и быстрее на фиксированных формах `[maxRoiCount, 3, H, W]`. Но фиксированная форма без
явной политики превращается в silent drop.

**Пример.** Коммит 2e9f8b3 «Add fixed-capacity OCR ROI prepare»: `Op_Onnx_ExtractObbToPaddleRec_FP32_NCHW` получил
`maxRoiCount`, `actualCountOutputKey` и `PaddleRecRoiOverflowPolicy`.

### 4.5. RISC плюс CISC

**Постулат.** Базовые geometry-ops (Crop, Resize, PadResize, Rotate90, Perspective, Undistort) это RISC. Fused macro-ops
допустимы для типичных hot path, но не заменяют RISC, а собирают проверенные примитивы в один граф.

**Почему.** Один ONNX-граф быстрее цепочки мелких инструкций: меньше ORT calls, промежуточных тензоров и синхронизаций.
RISC остаётся для нетипичных цепочек и для проверки CISC.

**Пример.** `Op_Onnx_BgrU8Hwc_To_RgbFP16Nchw_Div255` заменяет три VM-шага одним графом.
`Op_Onnx_ExtractObbToPaddleRec_FP32_NCHW` собирает crop + perspective + pad-resize + Paddle-нормализацию для N регионов
в один запуск. Его корректность проверяется сравнением с RISC-цепочкой в тестах.

### 4.6. Runtime-generated kernels кэшируются глобально, lazy, по полному ключу

**Постулат.** Kernel строится при init программы и попадает в общий кэш. Ключ включает kind, shape, тип, layout, все
параметры конструктора, влияющие на graph bytes, backend, opset и provider options. Кэш хранит только immutable
`OnnxModel`/`InferenceSession`; `RunOptions` и `IoBinding` отдельные на контекст.

**Почему.** Полная матрица `operation × type × layout × backend × shape` взрывается комбинаторно, но одинаковые kernels
между программами обязаны переиспользоваться. Неполный ключ для TensorRT отдаёт чужой engine с другой формой.

**Пример.** Коммит f5c746a «Cache generated ONNX operator sessions»: `RuntimeOnnxOperatorKernelCache` с ключом
`input=...;inputType=...;output=...;op=<GetCacheSemanticKey>`. `Perspective` включает в семантический ключ точки квада;
для runtime-операторов TensorRT engine cache принудительно `EnableEngineCache = false`. Из этого же постулата следует
дешевизна десяти контроллеров: одинаковые `Resize` делят одну сессию.

## 5. Именование как часть контракта

### 5.1. Geometry-ops именуются по типу и layout, color-ops полным форматом

**Постулат.** `Op_Onnx_Crop_FP16_NCHW`, без RGB/BGR. `Op_Onnx_BgrU8Hwc_To_RgbFP16Nchw_Div255` с полным описанием, что
меняется.

**Почему.** В trace должно быть сразу видно смешение FP16/FP32 и NCHW/NHWC. Geometry двигает оси и элементы, цвет не
читает, поэтому цвет в имени только вводит в заблуждение.

**Пример (так было / так стало).** Коммиты c0587cf «Fix mixed precision runtime paths» и 9888e1d «Fix FP16 box
extraction»: ошибки смешанной точности искали по коду, потому что из имени операции тип не был виден. После этого тип и
layout стали частью имени и появились отдельные классы на каждый вариант.

### 5.2. ONNX-типы не загрязняются VM-интерфейсами

**Постулат.** `YoloBox`, `YoloObb`, `OcrResult` используются как payload напрямую. Знание о VM и координатном маппинге
живёт в `Pipeline` и `Pipeline.ONNX`, а не в модельных структурах.

**Почему.** `NeuroModFlowNet.ONNX` это библиотека инференса, её потребители не обязаны знать про VM. Обратно: VM не должна
зависеть от доменных структур, иначе `Pipeline` перестаёт быть нейтральным.

**Пример.** Payload mapper-ы для `YoloBox`/`YoloObb`/`OcrQuadRegion` лежат в `Pipeline.ONNX/Coordinates`, а не как
методы у самих типов. Трекер и его типы ушли в отдельный `NeuroModFlowNet.CV` без зависимости от ONNX; при обсуждении
имя `IoUFrameTracker` в ONNX-слое было отвергнуто именно по этой причине.

## 6. Как пользоваться документом

- Новая VM-стадия или сервис: пройти по разделам 3 и 4 и проверить, какие постулаты она задевает.
- Появилась новая «грабля», из которой вырос новый принцип: добавить постулат в формате «постулат, почему, пример
  (так было / так стало)» сюда и в `AGENTS.md`.
- Плановая сверка с кодом: обновить дату вверху, отметить расхождения. Известные отложенные расхождения ведутся
  отдельно (`docs/TODO.md` и список P2/P4/P5/P6/P9/P10 из проектной памяти).
