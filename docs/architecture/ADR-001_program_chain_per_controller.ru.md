# ADR-001. Цепочка программ в одном контроллере вместо второй VM или switch по камере

Статус: **принято, реализовано** (2026-09-22).
Область: `NeuroModFlowNet.Pipeline` (`VmController`, `VmProgram`, `VmProgramBuilder`, `OpTraceEntry`).
Связано: `docs/Postulates.ru.md` (постулаты 3.1, 3.2), `docs/architecture/tracker_and_source_config.ru.md`.

## Контекст

Типовой сценарий: N камер, у каждой своя предобработка кадра на GPU (perspective, undistort, resize с разными
параметрами), после которой кадр идёт по общему пути (детекция, трекинг, OCR). Нужно, чтобы общая часть была
**одинаковой для всех камер как код**, а подготовка могла быть у каждой камеры своей.

Рассматривались варианты:

1. **Пред-VM на камеру + общая основная VM**, регистры переносятся вручную между контроллерами.
2. **Одна VM на все камеры** с новой операцией `switch` по `SourceId`, подпрограммами или inline-блоками и `goto` на
   общий участок.
3. **Один контроллер на камеру, один builder**, общая часть дублируется как экземпляры программы.
4. **Один контроллер на камеру, цепочка программ**: `[prepare_i, common]`, исполняемых одним контекстом.

## Решение

Принят вариант 4 как расширение варианта 3.

- `VmController` принимает `IReadOnlyList<VmProgram>` и исполняет программы по порядку **одним и тем же
  `VmRunContext`**. Конструктор с одной программой сохранён.
- `VmProgram.ExecuteAsync`/`ExecuteWarmupAsync` возвращают `VmProgramExit`: `Stopped`, если инструкция вернула
  `OpResultKind.Stop`, иначе `Completed`. `Stop` завершает весь запуск, оставшиеся программы цепочки не исполняются.
  `Fail` в любой программе проваливает запуск, как и раньше.
- Метки остаются локальными для каждой программы; jump через границу программ невозможен по построению.
- `VmProgram` получил необязательное `Name`, `VmProgramBuilder` принимает его в конструкторе, `OpTraceEntry` получил
  поле `Program`. В trace видно, к какой программе цепочки относится запись; `Index` остаётся локальным индексом.
- Warmup исполняет всю цепочку, dispose контроллера освобождает инструкции всех программ.

## Почему так

**Регистрам не нужно «переходить» между исполнителями.** `VmRunContext` это регистровый файл одного принятого запуска.
Если цепочка исполняется внутри одного контроллера, контекст просто передаётся следующей программе: тот же `RunId`, та
же `VmGlobalMemory`, те же disposable-выходы, те же sync gates. Семантически цепочка равна конкатенации инструкций, и
все гарантии VM сохраняются автоматически.

**Вариант 1 отвергнут**, потому что регистры пересекают границу владельца: общая VM получает одну `GlobalMemory` на все
камеры (состояние трекера пришлось бы ключевать по `SourceId`, что противоречит решению G2), sync gate общей VM
упорядочивает кадры разных камер в один поток, владение `OrtValue` между контекстами требует отдельного протокола,
trace и warmup рвутся на две половины.

**Вариант 2 отвергнут** по тем же причинам с другой стороны: один контроллер на все камеры означает общий `MaxInFlight`,
общий порядок `RunId` и общее состояние. Switch решает задачу «код», но не задачу «изоляция per-source», а именно она
главная. Плюс программа растёт в N раз и trace каждого кадра показывает N-1 пропущенных блоков.

**Вариант 3 остаётся основой**: контроллер = камера, общее между контроллерами это ресурсы (`IVmResource`, батчинг
модели) и глобальный кэш kernels (`RuntimeOnnxOperatorKernelCache`), а не программа и не память. Дорогое не
дублируется. Цепочка добавляет к нему только явную композицию «подготовка + общий путь» без склейки списков вручную.

## Контракт между программами

Контракт это имена регистров. `prepare` обязан оставить, например, `image.model` (FP16 NCHW на GPU) и
`transform.model` (обратное преобразование), `common` их читает. Проверка уже есть: `VarRequirement.Reads` первой
инструкции `common` и `DeviceCompatibilityValidator` в warmup. Несовпадение падает на старте, не на кадре.

## Что сознательно НЕ сделано

- **Общий экземпляр `common` между контроллерами.** «Одинаковая для всех» сегодня означает одинаковый код из одного
  builder-а, экземпляр у каждого контроллера свой. Причина: `Op_Onnx_TensorTransformBase` держит на экземпляр
  `IoBinding` и `RunOptions` (mutable native state) и `executionLock`. Общий экземпляр сериализовал бы все камеры на
  каждой geometry-операции. Чтобы шарить экземпляр, нужен отдельный шаг «чистый ROM»: вынести `IoBinding`/`RunOptions`
  из op-а в объект, принадлежащий запуску или контроллеру. Шаг независим от этого ADR.
- **Op вызова подпрограммы (`call`) и `switch`.** Композиция делается на этапе сборки контроллера, не в runtime.
- **Цепочка через границу контроллеров.** Если понадобится кросс-камерная логика (мульти-камерный трекинг, глобальный
  счётчик), границей должно быть typed CPU-значение через ресурс или очередь, а не передача `VmRunContext`.

## Последствия

- Существующий код с одной программой не меняется: перегрузка конструктора сохранена, `await program.ExecuteAsync(...)`
  без использования результата компилируется.
- Потребители `OpTraceEntry` (VMDebug labs) получают новое необязательное поле `Program`; старые вызовы совместимы.
- Тесты: `tests/NeuroModFlowNet.Pipeline.Tests/Execution/VmControllerProgramChainTests.cs` (общий контекст, `Stop`,
  `Fail`, локальные метки, warmup, dispose, пустая цепочка).
