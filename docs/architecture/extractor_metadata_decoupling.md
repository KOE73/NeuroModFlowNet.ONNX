# Архитектурное разделение метаданных модели и данных инференса

## Причины изменений (Reasons)
Ранее экстракторы (`IResultExtractor`) и их базовая логика жестко зависели от единого контекста выполнения (например, `OnnxRuntimeContext`), который совмещал в себе как статические метаданные о модели, так и динамические результаты инференса (`OrtValues`).

С развитием проекта и появлением потребности в интеграции с модулями из `NeuroModFlowNet.Pipeline.ONNX` возникла фундаментальная проблема:
1. **Прогрев (Warm-up) и Инициализация:** Для инициализации внутренних буферов экстрактора (пулы, массивы и т.д.) необходима только информация о форме (Shape) и типах (ElementDataType) выходных тензоров. Сами данные при этом не требуются.
2. **Маршалинг данных:** При получении каждого кадра из `OrtValue` чтение свойств вроде `.Shape` на каждом такте — это лишние накладные расходы. В новом пайплайне модель как таковая может быть недоступна, а на вход могут подаваться только "голые" `OrtValue`.

## Суть изменений (Implementation)

Мы разделили ответственность за предоставление данных на два независимых интерфейса:

### 1. `IModelMetadataProvider`
Отвечает исключительно за статическую информацию о модели. Доступен в момент подготовки пайплайна (Warm-up / SetModel).
- Содержит `PrimaryInputName` и `PrimaryOutputName` с реализацией по умолчанию (Default Interface Members), возвращающей первый элемент из списков `InputNames` и `OutputNames`. Это избавляет новые реализации от необходимости писать дублирующий код, сохраняя лаконичный API для моделей с одним входом/выходом.
- Содержит словари `ModelOutputShapes` и `OutputMetadata`.
- Позволяет экстрактору произвести `Init()` и `Check()`.
- Исключает доступ к самим тензорам.

### 2. `IOnnxModelOutputs`
Отвечает за динамические результаты инференса (каждый такт/кадр). Передается в метод `Extract(IOnnxModelOutputs outputs)`.
- Содержит методы для получения `ReadOnlySpan<T>` по имени выхода.
- Не содержит свойств модели, которые могли бы привести к лишнему маршалингу (например, `Shape` или `ElementDataType`).

## Следствия для архитектуры (Consequences)
*   **Изоляция**: Метод `Extract()` теперь работает только с интерфейсом, предоставляющим данные, и ничего не знает о самой сессии ONNX.
*   **Оптимизация**: Исключена возможность случайного чтения тяжеловесных метаданных `OrtValue` внутри горячего цикла (hot path) `Extract`. Вся инициализация (в том числе кэширование Shape и типов) строго перенесена в `Init() / Check()`.
*   **Интеграция**: В `NeuroModFlowNet.Pipeline.ONNX` теперь можно написать простую обертку над массивом `OrtValue`, реализующую `IOnnxModelOutputs`, и скормить её существующим экстракторам без изменения базовой логики библиотеки.

## Правила для разработчиков
1. **Инициализация**: Любая работа с формами тензоров (Shape), типами (Float16/Float) должна происходить внутри переопределенных методов `Init()` и `Check()`.
2. **Экстракция**: Метод `Extract(IOnnxModelOutputs outputs)` должен использовать **только** предварительно рассчитанные в `Init` размеры (например, `ItemCount`, `BatchCount`, `MaskPixels`) и вызывать методы наподобие `outputs.GetTensorDataAsSpan<T>(name)`.
3. **Запрет наследования**: `IOnnxModelOutputs` **не должен** наследовать `IModelMetadataProvider` или наоборот. Это два разных логических контекста (Время настройки vs Время выполнения).
