# План асинхронных программ VM и GPU-видеовыхода

Статус — проект архитектуры перед реализацией.

## 1. Целевая схема

Один контроллер на источник выполняет `[prepare, common]` в одном `VmRunContext` по [ADR-001](ADR-001_program_chain_per_controller.ru.md). `prepare` приводит данные источника к контракту `common`. У этого контроллера остаются порядок кадров, состояние трекера и собственные ограничения числа запусков.

Третья программа выполняет отрисовку отдельно, в том же процессе и тем же интерпретатором. Она получает выбранные значения и GPU-ресурс кадра. Планировщик может пропустить необязательную работу при нехватке ресурсов. Готовые кадры уходят в видеослужбу. Основной запуск завершается независимо от рисования, кодирования и доставки.

```text
источник → VmController [prepare → common] → завершение основного запуска
                                    └─ POST render → планировщик → пул render

пул render → видеослужба → GPU-композиция → NVENC → распределитель пакетов
                                                         ├─ очередь → MP4 → файл
                                                         └─ очередь → RTSP
```

Захват задаёт `SourceId` один раз. Среда исполнения автоматически переносит его через `POST` в доступном только для чтения заголовке. В заголовке также идут последовательность кадра, поколение подключения и исходный PTS, если он есть. Внутренний `RunId` получателя служит для его исполнения и трассировки. Для мозаики видеослужба использует отдельный `StreamId` и сохраняет `SourceId` кадров-источников. [Текущий VmRunIdentity](../../src/NeuroModFlowNet.Pipeline/Execution/VmRunIdentity.cs)

## 2. Тензорный регистр

Тонкая оболочка над `OrtValue` связывает три сущности.

- **Описанный формат** задаёт семантику данных. Для изображения это, например, порядок цветов, расположение осей и нормализация. Для тензора без пиксельной семантики достаточно его собственного контракта.
- **Фактическое представление** хранит тип элементов, форму, размещение и устройство. Для внешней видеоповерхности дополнительно могут понадобиться видимый размер, шаг строки и плоскости. Описание поверхности относится к её представлению в памяти.
- **Владение памятью** включает `OrtValue`, поддерживающего его владельца памяти и данные о готовности GPU, когда источник асинхронный. Для внешнего вида над NVDEC живут и обёртка ORT, и `AVFrame`. Для выделения через ORT живёт домен аллокатора до освобождения выданного ресурса. [Кадр NVDEC](../../labs/NeuroModFlowNet.Pipeline.Video.Nvdec/NvdecFrame.cs)

**Решение по перечислению.** Ввести небольшое перечисление для стандартных режимов нормализации изображения. Сохранить обозначения `Pos` для `0..1` и `Sym` для `-1..1`, уже используемые в проекте. Обязательность этого режима определяет контракт конкретного изображения. Для исходных байтов и тензоров общего назначения поле нормализации не требуется. Другие преобразования значений задаются явно параметрами конкретной операции. Видеодиапазон YUV и цветовая матрица описываются отдельно. Формат складывается из отдельных признаков, поэтому `BGR`, `FP16`, `NHWC`, `Pos` и `CUDA:0` можно проверять независимо. [Pos](../../src/NeuroModFlowNet.ONNX/Inputs/Algorithms/Pos/PosCvdnnFP32.cs) · [Sym](../../src/NeuroModFlowNet.ONNX/Inputs/Algorithms/Sym/SymCvdnnFP32.cs)

Операция записывает известные параметры при создании тензора. Фиксированный дескриптор переиспользуется. Для внешнего `OrtValue` и выхода с неизвестной фактической формой метаданные читаются у ORT один раз при приёме результата и сверяются с объявленным контрактом. Оси, порядок цветов и нормализацию объявляет производитель. Далее операции выбранной цепочки читают описание из регистра. Первый участок для переноса следует выбрать по реальному тракту `BGR U8 NHWC` и измерить число нативных запросов и выделений до и после. [Текущий запрос к ORT на горячем пути](../../src/NeuroModFlowNet.Pipeline.ONNX/Instructions/Operators/Op_Onnx_TensorTransformBase.cs)

Фабрика конвертеров принимает явную пару форматов и backend. При сборке связи она выбирает конкретную именованную операцию, проверяет поддержку и фиксирует выбор. Совместимые регистры передаются напрямую. Ошибка формата или backend завершает соответствующий запуск с диагностикой. В рабочем GPU-тракте пиксели остаются на GPU.

## 3. Именованные программы и `POST`

Программа объявляет именованные входы, их обязательность и, для тензоров и поверхностей, требуемый формат. Для обычных объектов CLR-тип в сигнатуре `POST` остаётся необязательным. При чтении свойств скриптом контракт задают сами чтения. Доступ к известным членам подготавливается при сборке или прогреве. Модуль, который производит закрытый тип, может предоставить адаптер. Отсутствующий необязательный вход остаётся пустым. Переданное значение проверяется по требованиям потребителя.

Построитель связи сначала сопоставляет точные имена входов и регистров. Для несовпадающих имён хост задаёт явное переименование в связке или у конкретного вызова. При сборке также разрешается имя программы, проверяются привязки и форматы, которые уже известны. Исполнение `POST` читает только указанные регистры. При допуске задачи планировщик создаёт входной контекст по готовой привязке. [Именованные входы VM](../../src/NeuroModFlowNet.Pipeline/Execution/VmRunInputs.cs) · [Требования к регистрам](../../src/NeuroModFlowNet.Pipeline/Instructions/VarRequirement.cs)

```text
render expects   frame, boxes, optional labels
common → render  frame ← MOVE image.rect, boxes ← detections, labels ← ocr.labels
common           POST render
```

Для первого варианта передачи ресурса использовать `MOVE`.

1. До передачи владения `POST` проверяет все аргументы и возможность каждого переноса. Перенос всех ресурсов подтверждается целиком. Два исключительных переноса одного владельца отклоняются как ошибка контракта.
2. В точке `POST` значения фиксируются, пакет становится владельцем перенесённых ресурсов. Путь `common → render` публикует этот пакет при успешном исходе основного запуска. `Stop` сохраняет текущую семантику VM. Если он выполнен до `POST`, публиковать нечего. При ошибке или отмене запуска уже подготовленный пакет освобождается.
3. Планировщик либо допускает пакет, либо принимает решение о его освобождении. Для отправителя выполненный `MOVE` окончателен, в том числе при отказе очереди. При вытеснении, истечении срока, отмене и закрытии очереди ответственность остаётся у владельца пакета. При старте исполнитель принимает владение. После постановки GPU-работы возврат в пул происходит после завершения её использования. Основная программа не ждёт очистки при выбросе пакета.

`VmRunContext` хранит имена регистров отдельно от ресурсов для освобождения. Поэтому перенос должен менять владение самим ресурсом в среде исполнения. [Текущее владение контекста](../../src/NeuroModFlowNet.Pipeline/Contexts/VmRunContext.cs)

`SHARE` оставить до появления задачи на совместное чтение одной поверхности. Его возможная реализация — одна удерживаемая ссылка на читателя и счётчик времени жизни буфера. Порядок записи остаётся свойством программы. При накладке автор меняет программу, в том числе может вынести `POST` после последней записи или явно создать другой буфер.

## 4. Пул и планировщик

У именованной программы есть фабрика и политика запуска. Для входной цепочки можно использовать тот же именованный способ подачи задания с `SourceId` в заголовке и `frame` во входах. Политика `ingest` направляет его в контроллер соответствующего источника, где уже работает `[prepare, common]`. Политика `render` направляет независимый кадр любому свободному исполнителю своего пула.

Пул создаёт и прогревает заданное число экземпляров `VmProgram` для выбранных режимов на старте. У каждого свои изменяемые нативные ресурсы, например `IoBinding`, `RunOptions` и контекст Direct2D. Бэкенд упорядочивает доступ к общему D3D11 immediate context, если он используется несколькими исполнителями. Неизменяемые сессии и kernels переиспользуются там, где это разрешает их контракт. На каждый пакет создаётся свежий контекст запуска. После завершения и подготовки к следующему запуску исполнитель возвращается в пул. Ресурсы экземпляров освобождаются при остановке после завершения GPU-работ и освобождения выданных ими буферов. Долгоживущие выходные поверхности может держать самостоятельный пул видеослужбы. [Раздельное состояние экземпляров](ADR-001_program_chain_per_controller.ru.md#что-сознательно-не-сделано)

Планировщик знает адресата, класс задачи, приоритет, срок, доступные ресурсы и политику очереди. Классы и их порядок назначает хост. Первый профиль отдаёт приоритет основному расчёту, кодирует готовый кадр к такту выхода и допускает отрисовку в пределах оставшегося бюджета.

- Для очереди рисования хранить не более одного ожидающего кадра на `(адресат, SourceId)`, заменять его более свежим и справедливо обходить активные источники. Отдельно ограничить зарезервированные и активные GPU-работы, поверхности и байты. Подготовка пакета к публикации также учитывается в этих пределах.
- По `SourceId`, поколению подключения и последовательности отбрасывать запоздавший результат, если более новый кадр уже стал последним готовым. Возраст результата проверяется отдельно. Кодирование использует только готовую поверхность. При наличии предыдущего кадра оно может закрыть такт без новой отрисовки по политике выхода.
- Раздельно учитывать CUDA/графическую работу, сессии NVENC, память и работу в полёте. Настраиваемые проценты выражают бюджет допуска на ресурс за окно измерения. Приоритет применяется при допуске новой работы. Контроль задержки основного пути и лимит уже отправленной фоновой работы задают поведение под нагрузкой.
- Трассировка связывает `POST` и исполнение по идентификатору кадра. Диагностика показывает место ожидания, причину пропуска, возраст завершившегося кадра и занятость пулов. Выбор класса или приоритета остаётся в конфигурации хоста.

## 5. Рисование и видеослужба

`render` получает кадр и заданную GPU-поверхность из пула. Его первые операции приводят кадр к формату поверхности через выбранную при сборке связи подготовку. Если конвертация нужна только видеоветви, она запускается после выбора конкретной заявки для исполнения. Уже подготовленный кадр можно передать через `MOVE` после последнего использования в `common`.

Первый вариант использует именованный C#-рисовальщик. В инструкции `DRAW DIRECT2D surface, "bags"` значение `surface` задаёт регистр GPU-поверхности, а `bags` — ключ регистрации `IDirect2DDrawer` в DI хоста. Хост разрешает ключ один раз при сборке каждого экземпляра `render`. Неизвестный ключ приводит к ошибке сборки программы.

Инструкция открывает проход `BeginDraw`–`EndDraw` и синхронно вызывает рисовальщик. На время вызова он получает `IVmRegisterReader` для чтения регистров текущего запуска и `IDirect2DCanvas` для рисования на выбранной GPU-поверхности. Рисовальщик определяет, какие регистры читать, какие примитивы рисовать, в каком порядке и с какими стилями. Координаты изображения выражаются в пикселях. Контракты и операция публичные, а `BagDrawer` и его DI-регистрация находятся в частном BagTracking. [Пример Direct2D](../../labs/NeuroModFlowNet.VideoOverlay/GpuOverlay.cpp)

В следующих этапах универсальный настраиваемый рисовальщик и рисовальщик на основе C#-скрипта с компиляцией при запуске могут стать отдельными реализациями `IDirect2DDrawer`. Настройки универсального рисовальщика задают чтение полей, слои и стили. Для переиспользуемых статических слоёв можно оценить `ID2D1CommandList`.

Опорная схема — рисовать один раз на кадре источника и переиспользовать оформленный кадр для выходов. В режиме с фиксированным размером текста в мозаике координаты вместе с кадром переводятся в систему выходной плитки, а текст рисуется на холсте выхода.

Видеослужба держит последний готовый кадр каждого подписанного источника. Кадр принадлежит ограниченному пулу с запасом для основного тракта. Настройки выхода задают crop, вписывание или квадрат, раскладку, разрешение, цветовое преобразование и FPS. У мозаики постоянный GPU-холст, где по мере поступления обновляются только изменившиеся плитки. На такте выхода кодировщик получает стабильную NV12-поверхность из пула. Её можно вернуть после подтверждения завершения кодирования.

- Один источник может следовать своему PTS или идти с фиксированным выходным FPS. У мозаики свой монотонный такт. При повторе кадра меняется выходной PTS. Исходное время кадра сохраняется. Профиль задаёт максимальный возраст и поведение при остановке источника.
- Один кодируемый профиль использует одну долгоживущую сессию. Несколько доставок одного профиля получают один сжатый поток. Выход с другим кодеком, разрешением или целевым битрейтом выбирает свой профиль.
- Служба отвечает за часы, маршруты, набор источников и ресурсы сессий. Планировщик отвечает за допуск GPU-работ. Кадр передаётся на аппаратный энкодер в GPU-памяти. Дальше тракт доставки работает со сжатыми пакетами независимо от времени жизни GPU-кадра.

### Контракт сжатого потока

Энкодер публикует описание потока и последовательность сжатых пакетов. Описание содержит `StreamId`, поколение, параметры кодека, формат битстрима и его конфигурацию, например SPS/PPS для H.264. При перезапуске энкодера или смене конфигурации начинается новое поколение. Распределитель хранит актуальное описание отдельно от очередей, чтобы при подключении или восстановлении выход сразу знал, какие пакеты может принять.

Пакет содержит общую ссылку на сжатые байты, поколение и порядковый номер, `PTS`, `DTS`, длительность, шкалу времени и признак подтверждённой точки произвольного доступа. Для H.264 единица очереди — целая access unit, по которой можно принимать решение о пропуске и возобновлении. Пакеты идут в порядке декодирования. Мультиплексор пересчитывает `PTS` и `DTS` в шкалу своего выхода, сохраняя их различия при переупорядочивании кадров. [FFmpeg AVPacket](https://ffmpeg.org/doxygen/trunk/structAVPacket.html) · [FFmpeg muxing](https://ffmpeg.org/doxygen/trunk/group__lavf__encoding.html)

Распределитель передаёт каждому выходу свою удерживаемую ссылку на неизменяемые сжатые байты через неблокирующий приём. Модуль, который меняет битстрим, создаёт свой результат. Локальные метки мультиплексора, например индекс дорожки, принадлежат этому выходу. При использовании FFmpeg ветка передаёт мультиплексору свою ссылку на `AVPacket`. Освобождение последней ссылки возвращает сжатый буфер. Буфер передачи должен жить независимо от входной поверхности и рабочего слота энкодера. [Владение пакетами FFmpeg](https://ffmpeg.org/doxygen/trunk/group__lavf__encoding.html)

### Модули и конфигурация выхода

Каждый выход собирается из подписки на кодируемый поток, собственной ограниченной очереди, цепочки фильтров битстрима при необходимости и модуля доставки. Адаптация битстрима отвечает за форму пакетов и размещение параметров кодека. Мультиплексор или пакетизатор добавляет заголовки контейнера либо транспорта. Модуль доставки ведёт файл или подключение. Один адаптер может совмещать эти функции, как FFmpeg RTSP muxer, который пакетизует в RTP и публикует поток на заданный RTSP-сервер. Конфигурация выбирает модули по имени, их порядок, параметры и адрес назначения. При запуске проверяется совместимость кодека и формы битстрима на каждой границе. [Фильтры битстрима FFmpeg](https://ffmpeg.org/ffmpeg-bitstream-filters.html) · [Публикация RTSP](https://ffmpeg.org/ffmpeg-protocols.html#rtsp)

```text
profile overview → encoder H.264 → раздача сжатых пакетов
    archive → очередь archive → MP4 mux → файл
    live    → очередь live    → нужная адаптация битстрима → RTSP publisher
```

Фильтры, заголовки и пересчёт времени идут в исполнительном контексте выхода. Например, упаковка Annex B может понадобиться одному потребителю, а другой использует конфигурацию кодека в заголовке контейнера. Для первого этапа достаточно реестра встроенных модулей с проверяемыми входами и выходами.

### Перегрузка и отказ назначения

- **Общий принцип.** У каждого выхода свой обработчик записи, пределы очереди по времени и байтам, сроки операций и политика восстановления. Повторное открытие выполняет тот же обработчик после завершения предыдущей попытки. Отказ одного выхода расходует только его ограниченный бюджет. В его диагностике видны заполнение очереди, возраст пакетов, отброшенные участки, последнее успешное действие и причина ошибки.
- **Сетевой выход.** При переполнении или разрыве очищается устаревшая очередь этой ветки. После подключения ветка ждёт подтверждённую точку входа с актуальной конфигурацией. Для первого H.264-профиля это IDR с соответствующими SPS/PPS в форме, которую требует получатель. Запросы от нескольких выходов на ближайший IDR можно объединить и ограничить по частоте. Энкодер продолжает обслуживать остальные подписки. [Пример возобновления в демке](../../labs/NeuroModFlowNet.VideoOverlay/CodecPreview.cpp)
- **Файловый выход.** При долгой остановке диска ограниченная очередь исчерпывается. Настройка определяет, остановить запись с диагностикой или возобновить её новым сегментом с отметкой разрыва. Уже закрытые сегменты остаются отдельно. Сетевой выход и основная обработка продолжаются.

При запуске нового поколения каждый выход обновляет конфигурацию и начинает запись или передачу с подходящей точки входа. При штатной остановке выход завершает запись в пределах заданного срока. Оставшиеся ссылки освобождаются при закрытии соответствующей очереди и модуля.

## 6. Разделение проектов и папок

Имена новых папок ориентировочные. Существующие классы остаются в своих проектах и перемещаются при подтверждённой необходимости.

| Проект | Папки и ответственность |
|---|---|
| `NeuroModFlowNet.Pipeline` | `Instructions/` для `POST` и существующего интерпретатора. `Execution/` для именованных связей, пакетов запуска и пула программ. `Scheduling/` для универсальной политики допуска. `Resources/` для протокола владения, если его нужно выразить на уровне VM. |
| `NeuroModFlowNet.Pipeline.ONNX` | `Tensors/` для `OrtValue`, описаний формата, привязки владельцев и импорта. `Instructions/Operators/` для явных преобразований и выбора реализации при инициализации. |
| `NeuroModFlowNet.ONNX.Graph` | `Builders/` для переиспользуемых ONNX-графов конверсии. |
| `NeuroModFlowNet.ONNX.Visualizer` | `Direct2D/` для `IDirect2DCanvas`, рендерера, ресурсов DirectWrite и исполнения GPU-композиции. Здесь остаются визуальные примитивы, стили и платформенный код отрисовки. |
| Новый `NeuroModFlowNet.Pipeline.Video` | `Instructions/` для тонких VM-адаптеров. `Rendering/` для программы `render` и контракта `IDirect2DDrawer`. `Frames/` для владения поверхностями. `Outputs/` для маршрутов, часов и сборки веток. `Encoding/` для кодировщиков. `Packets/` для описания сжатого потока, раздачи, владения пакетами и адаптации битстрима. `Sinks/` для контейнеров и доставки в файл или RTSP. `Windows/Interop/` для нативной стыковки CUDA и D3D11, синхронизации и передачи поверхности в рендерер. |
| `labs/NeuroModFlowNet.Pipeline.MultiCamera`, прикладные хосты | Сборка программ и политик исполнения, конфигурация именованных регистров и маршрутов. Прикладные хосты регистрируют рисовальщики и разрешают их ключи при сборке программ. Специфика камер, моделей и объектов остаётся в конфигурации и прикладных операциях хоста. |
| `labs/NeuroModFlowNet.VideoOverlay`, `labs/NeuroModFlowNet.Pipeline.WebDebug` | Лабораторные замеры и отладочный выбор точки наблюдения. Служба видеовыхода подключается из хоста напрямую. |

`Pipeline` остаётся базовой библиотекой. `Pipeline.ONNX` использует `Pipeline` и `ONNX.Graph`. `Pipeline.Video` связывает `Pipeline`, `Pipeline.ONNX` и `ONNX.Visualizer`. Рендерер принимает поверхность через контракт платформенного бэкенда, а его вызов выполняет адаптер видеоветви. Хосты собирают зависимости и выбирают бэкенд явно. Такое направление исключает циклические ссылки и привязку ядра к медиаформатам.

## 7. Порядок реализации и проверки

1. **Формат и владение на одном маршруте.** Выбрать цепочку с `BGR U8 NHWC`, провести дескриптор от создания до потребителя. Проверить статическую и динамическую форму, отказ на несовместимом формате, отсутствие новых переносов GPU ↔ CPU, корректное освобождение `OrtValue` с внешним владельцем. Замерить повторные запросы метаданных и аллокации. Изменение базового контракта VM или публичных типов вынести на согласование до реализации.
2. **Именованные входы, `POST MOVE` и очередь.** Сначала проверить на обычном освобождаемом ресурсе связывание имён, пропущенный необязательный аргумент, атомарность передачи, отклонение очередью, вытеснение, ошибку и остановку. Отдельно проверить публикацию при нормальном завершении, `Stop` до и после `POST`, ошибку и отмену. Затем проверить те же сценарии с реальным GPU-ресурсом и незавершённой работой. Сохранить тесты общего контекста и синхронизации для `[prepare, common]`.
3. **Один GPU-выход.** Соединить проверенный стык `CUDA OrtValue → ORT пишет BGRA в отображённый D3D11-буфер → D3D11-шейдер → Direct2D` с подготовкой `NV12` и NVENC. Начать с одного исполнителя. Проверить один реальный кадр из основной VM, геометрию и текст, соответствие устройств, отсутствие staging/readback пикселей и корректность освобождения поверхностей.
4. **Пул и нагрузка.** Сравнить один и несколько исполнителей с работающим инференсом. Варьировать число источников, их фазу прихода, разрешение и FPS. Сравнить основной тракт с выключенным и насыщенным видеовыходом по throughput, p95/p99 и пропускам. Отдельно измерить возраст видеокадра, количество вытеснений, задержку GPU и NVENC, пределы VRAM и очередей. По замеру определить допустимый бюджет и число сессий. Проверить справедливость, переподключение и завершение старого кадра после нового.
5. **Композиция и доставка.** Проверить постоянный холст, преобразование координат плитки, повтор кадра с новым выходным PTS и поведение при исчерпании поверхности. Подключить файл и RTSP к одному кодируемому профилю. Проверить независимые PTS/DTS и декодируемость обоих выходов, подключение после старта, переполнение очереди и возобновление по IDR, смену конфигурации, отказ сети и диска по отдельности. Проверить, что соседний выход продолжает работу, а при остановке освобождаются все ссылки на пакеты.

Проверять затронутые `tests`, `samples` и `labs` и собирать решение целиком после изменений ядра. Число сессий, размер пулов и пороги допуска фиксируются по замерам на целевом оборудовании.

### Исходный замер стыка CUDA и Direct2D

Отдельный стенд на RTX 5090 с ORT 1.30 подтвердил передачу синтетического CUDA `OrtValue` на D3D11-поверхность и рисование десяти рамок с подписями. Для `1920×1080` получены p50/p95 `0,879/1,420 мс` с CUDA 12 и `0,816/1,692 мс` с CUDA 13. В каждом режиме 10 прогревочных и 60 измеренных кадров в одном потоке. Время включает отображение буфера, запись через ORT, D3D11-шейдер, рисование и ожидание fence. Этот замер покрывает участок до готовой поверхности. Совместную нагрузку с инференсом, декодером и NVENC проверяем отдельно на этапах 3–5.
