# NeuroModFlowNet.Pipeline Architecture

Базовая модель:

```text
Host loop / event-system module
  -> решает, принимать ли работу
  -> передает named inputs в VM

PipelineVmController (один на источник)
  -> выдает плотный RunId
  -> запускает цепочку программ одним run context

PipelineProgram (одна или цепочка [prepare, common])
  -> линейный timeline инструкций
  -> labels и jumps, локальные для программы

PipelineRunContext
  -> локальные именованные регистры одного accepted run
  -> владеет временными ресурсами

PipelineGlobalMemory
  -> per-source config (калибровка, зоны, пороги), tracker state, resource registry, sinks, общие сервисы
```

Per-source config и per-source state (например состояние трекера) живут в `PipelineGlobalMemory`, потому что она
принадлежит контроллеру источника, а не одному run. Инструкции держат только ключи и читают значения на исполнении;
это позволяет держать набор инструкций (рецепт) одинаковым для всех камер, а различия физического мира (перспектива,
дисторсия, `StartZone`/`EndZone`, пороги) хранить как данные. Детали контракта и синхронизации последовательного
трекера: `docs/architecture/tracker_and_source_config.ru.md`.

VM не владеет источником кадров. Для видео host кладет `source.frame`, `source.id`, timing и другие входы в
`PipelineRunInputs`. Для другой предметной области набор входов может быть вообще не связан с изображениями.

## Почему цепочка программ, а не вторая VM и не switch по камере

Контроллер может исполнять несколько программ для одного принятого запуска одним и тем же `VmRunContext`. Регистровому
файлу не нужно «переходить» к другому исполнителю: тот же `RunId`, та же `GlobalMemory`, те же sync gates и
disposable-выходы. Это позволяет собрать `[prepare_camera, common]`, где подготовка своя у каждой камеры, а общая часть
одинакова как код. Вторая VM или один контроллер со switch по `SourceId` ломают изоляцию по источнику (общая память,
общий порядок `RunId`, общий `MaxInFlight`). Экземпляры программ между контроллерами не разделяются, потому что инструкции
могут владеть mutable native-состоянием; дорогое разделяется через ресурсы и кэш kernels. Подробно:
`docs/architecture/ADR-001_program_chain_per_controller.ru.md`.

## Почему RunId, а не frame number

Кадры могут быть пропущены до запуска VM. Если синхронизация будет ждать номер кадра, которого VM никогда не запускала,
ordered-точка зависнет. Поэтому синхронизация строится только по `RunId`, который выдается каждому принятому запуску.

## Почему string keys

Внешний контракт остается строковым: JSON, скрипты и диагностика работают по именам. Внутренняя компиляция имен в быстрые
слоты возможна позже, но публичная модель от этого не должна меняться.

## Почему trace внутри VM

Каждая инструкция измеряется отдельно и оставляет снимок переменных после выполнения. Снимок содержит тип, грубое место
памяти (`Cpu`, `Gpu`, `ExternalDevice`, `OrtValueUnknownDevice`, `Unknown`) и форму там, где ее можно получить без
тяжелой конвертации. Это нужно не для красивой статистики, а для контроля главной цели: видеть, какие данные уже живут на
GPU и где все еще происходит возврат в CPU-представления.

## Почему именованные transform-регистры

Жесткая структура вроде `scale/pad` подходит только для letterbox. Реальная обработка может включать crop, resize,
rotation, perspective, nonlinear warp и custom-преобразования. Поэтому transform является обычной именованной
переменной VM, а программа явно вызывает инструкции пересчета координат в нужном порядке. Промежуточные координатные
регистры остаются видимыми и могут использоваться следующими инструкциями.
